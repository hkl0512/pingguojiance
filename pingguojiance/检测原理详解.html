00一句话原理

人挑苹果时，眼睛其实只做了三件判断：颜色正不正、表皮亮不亮、有没有坏点。 这三件事全都可以用像素算出来——只要你能把「苹果」从画面里单独抠出来。

你的直觉可计算的量物理含义
颜色正饱和度均值、色相一致性色素浓度是否足够、成熟度是否均匀
表皮亮高光像素占比蜡质层是否完好 → 是否失水发糠
没坏点瑕疵像素占比 + 处数碰伤、褐变、腐烂的可见面积
长得周正二阶矩长短轴比、外接框填充率果形是否接近圆形
所以整件事的难点只有两个

第一，把苹果从背景里抠干净（环节 2–5）；第二，把「阴影」和「坏点」分开（环节 7）。 剩下的都是加减乘除。第二点是全篇技术含量最高的地方，后面会重点讲。

数据形态的变化很清楚：图片文件 → W×H×4 的字节数组 → 每像素的 H/S/V/L → 一张 0/1 的果实掩码 → 一张 0/1 的瑕疵掩码 → 4 个分数 → 1 个总分。

中间所有产物都是一维数组（长度 W*H），下标 i = y*W + x。 这是图像处理里最省事的写法：不需要二维数组，内存连续、遍历快。

02环节一：读图与降采样

做什么

把用户给的文件变成一张能逐像素读取的位图，并缩到最长边 420 像素。

怎么写

// 关键：顺手处理手机照片的 EXIF 旋屏，否则竖拍的苹果会躺着
const bmp = await createImageBitmap(file, { imageOrientation: 'from-image' });

const scale = Math.min(1, 420 / Math.max(sw, sh));
const W = Math.round(sw * scale), H = Math.round(sh * scale);

const cnv = document.createElement('canvas');
cnv.width = W; cnv.height = H;
const ctx = cnv.getContext('2d', { willReadFrequently: true });
ctx.drawImage(src, 0, 0, W, H);

const imgData = ctx.getImageData(0, 0, W, H);   // imgData.data 是 Uint8ClampedArray，长度 W*H*4
为什么一定要缩小

一张 4000×3000 的手机照片有 1200 万像素。后面每个环节都要遍历它好几遍，一次分析要跑几秒甚至十几秒。 缩到 420 大概 17 万像素，快了 70 倍，而信息量几乎没损失——判断苹果好坏用不到那么高的分辨率。

附带的好处

缩放本身就是一次低通滤波：JPEG 压缩块噪声、传感器噪点、表皮细微纹路都被平均掉了。 这直接减少了后面「把噪点当瑕疵」的误判。所以降采样不只是为了快，也是精度手段。

坑：420 是不是太糊了？

算一下：420px 图上一个直径 200px 的苹果，1% 果面面积 ≈ 直径 20px 的圆。 真实碰伤一般比这个大，所以 420 够用。但如果苹果只占画面 1/5，果径就只剩 80px，最小可分辨瑕疵缩到 8px——这就是页面上提示「把苹果拍大一点」的真实原因。

03环节二：转 HSV，并初筛出「像苹果的像素」

做什么

每个像素从 RGB 转成 H/S/V，同时给出一张「这个像素像不像苹果」的 0/1 掩码。

怎么写

const mx = Math.max(r, g, b), mn = Math.min(r, g, b), df = mx - mn;

// 色相 H：0–360°，红=0/360，黄=60，绿=120，青=180，蓝=240，品红=300
let hu = 0;
if (df > 1e-6){
  if      (mx === r) hu = ((g - b) / df) % 6;
  else if (mx === g) hu = (b - r) / df + 2;
  else               hu = (r - g) / df + 4;
  hu *= 60; if (hu < 0) hu += 360;
}
const s = mx > 0 ? df / mx : 0;     // 饱和度：颜色有多"浓"
const v = mx;                       // 明度：有多"亮"
const lum = 0.299*r + 0.587*g + 0.114*b;   // 人眼感知亮度

// 苹果色系：红(0±) 一路到黄绿(155)，把青蓝紫挡在外面；同时排除过暗和灰白
isFruit[i] = (mx > 0.09 && s > 0.16 && (hu <= 155 || hu >= 318)) ? 1 : 0;
为什么用 HSV 而不是 RGB

因为 RGB 的三个通道互相纠缠：光线暗一半，三个通道一起减半，颜色明明没变，RGB 距离却拉得很大。 而 HSV 把「是什么颜色」（H）、「颜色多浓」（S）、「有多亮」（V）拆开了，光照变化主要落在 V 上，H 和 S 相对稳定。

这就是它能扛住「苹果一半被阴影盖住」的根本原因——阴影只是让 V 变小，H 不变。

为什么色相范围是「≤155 或 ≥318」

苹果的可食用部分基本落在红—橙—黄—黄绿这一段。155° 之后是青绿到青色（来路不明的背景、蓝色桌布）， 318° 之前是紫红（很少有苹果是紫的）。这样一刀切掉，能把最常见的蓝桌布、灰墙、天空挡在外面。

坑：这一步只是「初筛」，不是「分割」

看着像苹果的像素可能包括：红桌布、木地板、人的手、旁边的另一个苹果、番茄。 所以这一步的输出必然是有噪声的，真正把苹果挑出来的是下一个环节。

04环节三：取最大连通域，锁定那个苹果

做什么

在掩码里找出所有「连成一片」的区域，只保留面积最大的那块，其余全部丢弃。

怎么写

本质是洪水填充（BFS/DFS）：从一个未访问的命中像素出发，把和它四邻接的所有命中像素都染成同一个编号，染完一片就是一块连通域。

for (每个未访问的命中像素 i){
  label++; sp = 0; stack[sp++] = i; label[i] = label;   // 用数组当栈，避免递归爆栈
  while (sp > 0){
    p = stack[--sp]; size++;
    x = p % W; y = (p - x) / W;                          // 一维下标还原二维坐标
    if (x > 0   && mask[p-1] && !label[p-1]) { label[p-1] = label; stack[sp++] = p-1; }
    if (x < W-1 && mask[p+1] && !label[p+1]) { label[p+1] = label; stack[sp++] = p+1; }
    if (p >= W  && mask[p-W] && !label[p-W]) { label[p-W] = label; stack[sp++] = p-W; }
    if (p < N-W && mask[p+W] && !label[p+W]) { label[p+W] = label; stack[sp++] = p+W; }
  }
  if (size > best) best = label;
}
为什么这一步能干净地解决问题

因为真实的苹果是一整块，而干扰物（桌布、手、番茄）要么面积更小，要么和苹果不连通。 「最大连通域」这一条假设，就把 90% 的背景干扰自动消掉了，不需要任何机器学习。

坑：叶子、果柄会破坏连通性

果柄偏褐、叶子偏绿，都可能被初筛判成「不算果实」，于是苹果主体和叶柄被切开——这没关系，最大块还是苹果本体。 真正麻烦的是下一步要解决的：苹果内部也会被切开。

05环节四：补洞

问题从哪来

苹果上最亮的那块反光，饱和度极低（接近白色），在环节二的初筛里会被判成「不像苹果」。 于是掩码上的苹果变成一个甜甜圈——中间空心。

空心会带来两个后果：那块高光区域不参与统计（光泽算不准），形状二阶矩也会偏；最坏情况下苹果被切成两个半环，最大连通域只剩半边。

怎么写

技巧：从图像四条边界开始灌水，凡是能灌到的「非果实」像素，就是真正的背景；灌不到的非果实像素，就是被果实包住的洞。 

// 1) 四条边上的非果实像素全部入栈，标记为 outside
for (x…) { push(x); push((H-1)*W + x); }
for (y…) { push(y*W); push(y*W + W - 1); }

// 2) 四邻接扩散，只扩散到"非果实且未标记"的像素
while (sp > 0){ … }

// 3) 既不是果实、又灌不到 → 是被包住的洞，补成 1
out[i] = (mask[i] || !outside[i]) ? 1 : 0;
为什么这招好用

它利用了拓扑学里一个很朴素的结论：洞＝被包围的区域，包围它的东西连不到图像边界。 所以不需要判断「这个洞是不是高光」，只要它被苹果包住，就一定是苹果的一部分。判断标准简单且鲁棒。

06环节五：边缘内缩（腐蚀）

做什么

把果实掩码的边界往里收一圈，收掉「果径的 5%」，得到一个更小的「分析区」。

const er = Math.max(4, Math.round(Math.sqrt(covered / Math.PI) * 0.05));
const inner = erode(filled, W, H, er);   // covered 是果实像素数，开方近似半径

实现上用的是可分离腐蚀：先横向取窗口内最小值，再纵向取一次，等价于方形核，但复杂度从 O(N·r²) 降到 O(N·r)。

为什么这一圈必须去掉（这是最容易被忽略的一步）

苹果和背景的交界处不是一刀切的，而是一条 3–10 像素宽的混合带：抗锯齿、镜头虚化、逆光边缘，都会让这条带上的像素「红里带灰」。

这些混合像素恰好同时满足「变暗 + 掉饱和度 + 色相偏移」——和淤伤的特征几乎一模一样。 我在测试里第一次跑，好苹果被判出 2 处瑕疵，位置全在左右轮廓线上，就是这条带造成的。

为什么取 5% 而不是固定像素

因为混合带的宽度和果径成正比，而不是和图片分辨率成正比。 苹果占画面一半和占画面十分之一，同一个手机拍出来，混合带都是果径的百分之几。取相对值才稳定。

07环节六：统计四组特征

只扫一遍分析区，把四项指标全都累加出来。

① 饱和度与明度均值

meanSat = sumSat / area;   meanVal = sumVal / area;

用来算「色泽」——颜色太淡、发灰，说明不新鲜或没熟透。

② 高光占比

if (val > 0.88 && sat < 0.30) hiCount++;   // 很亮且接近无色 = 镜面反光
highlightFrac = hiCount / area;
为什么光泽能反映新鲜度

苹果表皮有一层天然蜡质，完好时会形成小而集中的镜面高光。存放久了蜡质退化、失水，表面变糙，高光就散掉、消失。 反过来，如果高光面积特别大，多半是人工打蜡或者拍摄过曝。所以这个指标是个「倒 U」形：太少扣分，太多也扣分。

③ 色相一致性（圆统计）

这里有个陷阱：色相是环形的。350° 和 10° 只差 20°，但直接算平均会得到 180°（青色），完全错。 正确做法是把每个角度当成单位圆上的一个向量，先求和再取角度：

加权合成向量：  Z = Σ wᵢ·(cos θᵢ + i·sin θᵢ)
集中度：  R = |Z| / Σ wᵢ   (0 表示颜色杂乱，1 表示完全一致)
环形标准差：  σ = √(−2·ln R)   （弧度，代码里换算成度）

权重 w = sat × (0.4 + val)：越鲜艳、越亮的像素说话越有分量，暗部和灰边不参与拉低一致性。 主色相直接用合成向量的方向 atan2(Σsin, Σcos) 得到，后面判瑕疵要用。

④ 形状：二阶矩

把分析区看成一块薄板，算它的惯性张量，两个特征值对应长短轴：

λ₁,₂ = (mxx + myy)/2 ± √((mxx + myy)²/4 − (mxx·myy − mxy²))
roundness = √(λ₂ / λ₁)   → 圆是 1，越扁越小
外接框填充率 = 面积 / (宽×高)   → 正圆的理论值 π/4 ≈ 0.785

判分时拿两者和理论值比：偏离 0.785 越多，说明果形越不规整。

08环节七：判定瑕疵像素（全篇核心）

先想清楚：凭什么区分「阴影」和「淤伤」

这是整个项目最关键的推理。两者都很暗，只看亮度必然混淆。区别在颜色的变化方式：

成因色彩模型结果
阴影 光少了 RGB 三个通道同乘一个系数 k<1 V 变小，S 几乎不变，H 不变
淤伤 / 褐变 细胞破裂、氧化、失水 相当于混入一份灰褐色：c′ = α·c + (1−α)·brown V 变小，S 明显下降，H 往橙褐方向偏移

推导一下就明白：S = (max−min)/max，三个通道同乘 k 后分子分母同时乘 k，S 完全抵消。 而「混入褐色」是加法，分子变小、分母也变，S 一定会掉。

结论

「饱和度下降」才是淤伤的指纹，不是「变暗」。 这一条想通了，后面三个判据就是自然推论。

亮度基准：为什么用 75 分位而不是平均值

// 64 桶直方图，找累积到 75% 的那个亮度
var accH = 0, p75 = 0.6;
for (var hb = 0; hb < 64; hb++){
  accH += hist[hb];
  if (accH >= area * 0.75){ p75 = (hb + 0.5) / 64; break; }
}
  • 用平均值不行：平均值会被阴影面和瑕疵本身拖低，导致「变暗」的落差算不出来——瑕疵把自己当成了基准。
  • 用最大值不行：单个过曝像素或噪点就能顶到 1.0。
  • 75 分位代表「这个苹果受光良好的那部分表面的亮度」，是一个稳定的参照系。

三个判据，满足其一即判为瑕疵

var val0 = val[i];
if (val0 > 0.86) continue;                  // ① 太亮的直接放过：高光不可能是瑕疵

var darkRel = p75 - lum[i];
if (darkRel <= darkGate) continue;          // ② 不够暗的直接放过：正常受光面不可能是瑕疵

var dh = Math.abs(((hue[i] - dominantHue + 540) % 360) - 180);   // 与主色的角度差
var desat = meanSat - sat[i];                                     // 掉了多少饱和度

var browner  = dh > hueTol;                              // ③ 偏褐：颜色往橙褐跑了
var duller   = desat > desatGate;                        // ④ 褪色：失去鲜艳度
var blackRot = val0 < 0.20 && darkRel > darkGate * 2;    // ⑤ 黑斑：已经烂了

if (browner || duller || blackRot) defect[i] = 1;

三个判据各自负责一类瑕疵：

  • browner —— 褐变、氧化、晒伤、老化的浅褐色斑。
  • duller —— 新发生的磕碰（还没变褐，但组织已经失水发灰）、水渍、果霜。
  • blackRot —— 已经发黑的腐烂点、虫眼。
坑：为什么不用「局部对比度」找暗斑

我的第一版是这么写的：算每个像素周围 9×9 的平均亮度，比它暗很多就算暗斑。听起来很标准，跑出来坏苹果 94 分。

原因很直观：一块直径 80 像素的淤伤，9×9 的窗口整个都在淤伤内部，窗口均值≈这个像素自己，落差≈0。 局部对比度只看得到「小块」，看不到「大块」。这就是为什么改成用整果的 75 分位做基准——基准必须比瑕疵本身大一个量级。

取舍：为什么不干脆「所有暗的都算瑕疵」

因为苹果被侧光照时，暗面本身就比亮面暗 40%。加上这一条，好苹果会被判成大花脸。 所以「暗」只是必要条件（darkRel > darkGate），真正定性要靠色相和饱和度。

09环节八：聚类与排除误判

聚类：把散点合并成「一处瑕疵」

逐像素判完，得到的是成千上万个零散的 1。它们可能来自同一块淤伤的纹理、也可能是噪点。 用和环节三一样的连通域算法合并，就得到「几处瑕疵、各自多大、中心在哪」： 

if (cnt >= minArea && rim === 0)  list.push({ area: cnt, cx: sx/cnt, cy: sy/cnt });
//   面积够大         没碰到图像边界    记录面积与质心（用来画圈）
  • minArea 随灵敏度变化：标准档约为果面面积的 0.1%（5 万像素的苹果 → 约 48 像素的块）。小到看不出来的点直接丢掉。
  • rim === 0：碰到图像边框的块一律丢弃——那多半是背景没抠干净留下的残渣。

排除果柄和萼洼

// 以果实中心和宽高做归一化坐标
var nx = (c.cx - cx) / bw, ny = (c.cy - cy) / bh;
return !(Math.abs(nx) < 0.18 && (ny < -0.34 || ny > 0.34));
为什么必须排除

苹果顶部有果柄的凹窝，底部有萼洼，它们本身就是天然的黑褐色凹陷，会稳定触发 browner 和 blackRot。 不排除的话，每一个正常苹果都会被扣掉一处「瑕疵」。这是一个典型的「模型很准但场景不认」的例子—— 算法没错，是它不知道生物学常识。

10环节九：打分与分级

四个分项各自算分，再加权。所有分项都归一到 0–100。

完好度（权重 0.46）

完好度 = 100 · e−24·r − 4.5·n    （r = 瑕疵面积占比，n = 瑕疵处数）
r=1% → 79  |  r=3% → 49  |  r=5% → 30  |  r=10% → 9

为什么用指数衰减而不是线性扣分？因为「面积」和「严重程度」不是线性关系： 1% 的瑕疵不痛不痒，3% 就已经明显影响观感，10% 基本不能要了。指数函数正好把这个直觉变成曲线， 而且永远不会掉到负数。再按「处数」额外扣一点——三块小斑点比一块同样面积的大斑更烦人。

色泽（权重 0.27）

鲜艳度 = clamp((meanSat − 0.14) / 0.58)
亮度分 = exp(−((meanVal − 0.56) / 0.30)²)   // 高斯，太暗太亮都扣分
均匀度 = clamp(1 − hueStd / 42)
色泽 = 100 × (0.44·鲜艳度 + 0.24·亮度分 + 0.32·均匀度)

光泽（权重 0.13，倒 U 形分段）

高光占比得分解释
< 0.15%50几乎没有反光，失水发糠或表面太糙
0.15% – 5.5%72 → 100越接近 5% 越像「新鲜、蜡质完好」
5.5% – 15%100 → 74反光过多，可能打蜡或过曝
> 15%42大面积镜面反光，基本拍糊了

果形（权重 0.14）

果形 = 100 × (0.6 · clamp(roundness × 1.35) + 0.4 · fillScore)

总分与分级

总分 = 0.46·完好度 + 0.27·色泽 + 0.13·光泽 + 0.14·果形   （瑕疵面积 >10% 再额外 −6）
分数等级文案
≥ 85特级这是个好苹果
72 – 84良好算是个好苹果
58 – 71一般一般般，建议尽快吃掉
< 58较差不太行，建议换一个

权重的含义：「完好」最重要（0.46），因为烂一点就不能吃；颜色次之（0.27）， 它反映成熟度；光泽和形状加起来 0.27，属于「锦上添花」——长得丑但没坏的苹果，依然是能吃的苹果。

11五个关键设计决策，为什么是对的

1. 用 HSV 而不是 RGB 距离

RGB 是「设备语言」，HSV 更接近「人的语言」。判断颜色变化时，只有 HSV 能把光照和色料分开。

2. 用「最大连通域」而不是直接统计全图

省掉了最难的实例分割问题，代价是「画面里有多个苹果时会只认最大那个」。这是有意为之的取舍：先解决 80% 的场景，别一上来就追求通用。

3. 用 p75 而不是 mean / max 做亮度基准

基准必须不受「被检测对象」影响。mean 会被瑕疵拉低，max 会被噪点抬高，p75 接近「受光良好的表面」。

4. 用饱和度下降做淤伤指纹

因为它有物理依据（乘法 vs 加法混合），不是拍脑袋的阈值。有物理依据的特征，换一批照片往往还能用。

5. 边缘内缩按果径取相对值

因为误差源（虚焦、抗锯齿）的尺度跟物体大小相关，不跟分辨率相关。所有「尺度相关」的参数都应该写成相对值。

12调参实录：三版迭代

这一节是我真实的踩坑顺序，比结论更有用。

第一版：局部对比度找暗斑 → 失败

  • 做法：9×9 邻域均值 − 像素亮度 > 阈值 判为暗斑。
  • 结果：好苹果 91 分，坏苹果 94 分——完全反了。
  • 原因：大淤伤比检测窗口还大，窗口均值被瑕疵自身污染，落差趋近 0。
  • 教训：局部算子只能检测「比邻域小」的异常。检测大面积异常，参照系必须更大。

第二版：改用加权综合异常度 → 部分失败

  • 做法：0.42·偏色 + 0.33·变暗 + 0.25·褪色，超过 0.5 判瑕疵。
  • 结果：坏苹果只检出 4 个像素。
  • 原因：三个线索都只是「中等强度」时，加权后刚好压在阈值下面；而且阈值一调高，好苹果的边缘过渡带就冒出来了。
  • 教训：加权求和适合做排序，不适合做布尔判定。判定用「并联的弱条件 + 一个强前置门槛」更稳。

第三版（现行）：三条件并联 + 两道门槛 → 通过

  • 门槛：必须够暗（darkRel > darkGate）且不够亮（val < 0.86）。
  • 判定：偏褐 / 褪色 / 黑斑，任一成立即算。
  • 修边缘：腐蚀果径 5% 去掉过渡带（好苹果的 2 处误报就在这里消失）。
  • 实测：好苹果 92、青苹果 92、带三处淤伤的苹果 61（瑕疵占果面 3.66%）。
可复用的经验

1）先做能出数字的测试，别靠肉眼调参；
2）每次只改一个变量，并保留「好样本」作为回归测试——我每改一次都跑同样的三个苹果；
3）误报优先于漏报：好苹果被冤枉比坏苹果漏掉更伤用户信任，所以宁可门槛偏保守。

14自己验证：把算法抽出来跑

不想开浏览器也能测。核心函数 computeFeatures(d, W, H, canvas, sens) 只依赖第一参数（原始像素数组）， 所以可以把整段算法从 HTML 里切出来，用 Node 直接喂合成像素： 

const html = fs.readFileSync('index.html', 'utf8');
const a = html.indexOf('/* ---------- 核心算法 ---------- */');
const b = html.indexOf('/* ================= 渲染 ================= */');

// 把算法段包成模块，注入 clamp01 依赖
const { computeFeatures } = new Function('clamp01', html.slice(a, b) + '\n return { computeFeatures };')(clamp01);

// 造一个 460×460 的合成苹果：径向渐变 + 高光 + 可选淤伤
const img = makeApple('good');
const res = computeFeatures(img.data, img.W, img.H, null, 3);
console.log(res.score, res.dims, res.defectRatio);

这套「切出来跑」的办法有两个好处：毫秒级反馈（不用等浏览器）， 以及可以构造极端样本（纯青苹果、只有一处小斑、全黑图片），把边界情况一次性测完。

建议的回归样本集

至少准备 6 个：好红苹果、好青苹果、轻微磕碰、明显褐斑、腐烂黑点、非苹果图片（应该返回「没识别到果实」）。 每次调参都跑一遍，看这 6 个的分数有没有跑偏。

15想更准：从规则换成真模型

启发式方法的天花板很清楚：它只认「颜色统计意义上像不像坏」。要突破，得让模型自己学特征。

路线图

  1. 收集数据：同一苹果拍多角度、多光照。每类至少 300–500 张。标注只需要粗分类：好 / 轻微碰伤 / 明显腐烂 / 虫眼。
  2. 迁移学习：MobileNetV3-Small 或 EfficientNet-Lite，输入 224×224，冻结主干先训分类头，再解冻微调。桌面端几十分钟就能出第一个版本。
  3. 数据增强：亮度/色温抖动、随机裁剪、旋转、换背景。换背景这条最关键——它逼模型学苹果而不是学桌子。
  4. 导出前端：转成 TensorFlow.js（或 ONNX → onnxruntime-web），页面里 await tf.loadLayersModel(...)。
  5. 混合架构：模型给「类别概率」，现有规则给「瑕疵位置和面积」。两者互为兜底——模型加载失败时退回规则，规则拿不准时参考模型。
别丢掉可解释性

规则版最有价值的不是精度，而是它能说清「为什么扣分」——「检测到 3 处褐变，占果面 3.7%」。 换成黑盒模型后，建议保留瑕疵像素可视化，让用户仍然能看见依据。

18常见问题

为什么不直接用「红不红」判断？

青苹果也得好吃。所以判的不是「够不够红」，而是「颜色是否饱和、均匀」——红苹果看红的浓度，青苹果看绿的浓度，逻辑是统一的。

为什么照片里的苹果必须占大比例？

因为最小可检测瑕疵 ≈ 果径的 2%。苹果越小，可分辨的瑕疵就越大，小斑点直接看不见了。

为什么两个苹果一起拍只出一个结果？

最大连通域只保留一块。要支持多果，把环节三改成「保留所有面积 > 阈值 的连通域」，然后对每块分别跑环节六到九。

能识别虫眼吗？

直径足够大的虫眼会被「黑斑」判据抓到；毫米级的小孔在 420 分辨率下基本消失。想抓虫眼需要更高分辨率 + 专门的纹理分析。

为什么结果里经常出现「疑似」两个字？

因为这些都是从像素反推的统计判断，不是真的摸过、切开过。说「疑似」是诚实的说法。

想改风格 / 换判断口径怎么办？

全部参数集中在 computeFeatures 里，权重在 total = ... 那几行。想让「完好」更重要就调 0.46；想让分数更宽松就把指数系数从 24 降到 16。
